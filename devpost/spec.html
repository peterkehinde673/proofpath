Build With AI · Technical specification · Draft

A small local app, one live AI request, and no case database.

The PRD said what ProofPath should do. This blueprint shows where each part lives, how evidence moves through the analysis, and how the project stays small enough to build and demonstrate.

Architecture and data flow

The API key stays on the local server

Browser code is visible to people who open the page, so the secret key lives in an ignored local .env file and is read only by Node. The server checks the files, asks Gemini for structured analysis, checks its source references, and returns the result to the browser.

Browser workspace

Demo or selected files; review, timeline, report.

↓ Local Node server

Checks types and sizes, keeps the API key in .env, validates source IDs, and does not save uploads.

↓ Gemini API

One structured analysis request for text, image, and PDF evidence.

↩ Validated result

Returns to the browser as timeline, evidence details, and report.

Step through the build path

One result powers the timeline and report

1 · Start with demo or upload

Files: public/index.html, public/app.js, public/demo/*.txt. Demo opens the analysis after its live request; uploads show a review list first.

PRD: Entry and Evidence Selection.

2 · Check and send evidence

File: server.mjs. Allow up to five files, 2 MB each, 10 MB total, using TXT, PDF, PNG, or JPG. Reject unsupported or obviously invalid inputs and continue with remaining valid files when possible.

PRD: Entry and Evidence Selection; States and Boundaries.

3 · Ask Gemini once

Service: Gemini 3.1 Flash-Lite. A focused instruction and evidence parts request summary, dated events, direct source IDs/details, uncertain/missing items, and contradictions. JSON schema controls shape; it does not prove factual correctness.

PRD: Analysis and Evidence Timeline.

4 · Validate before display

File: server.mjs. Check JSON shape, submitted file IDs, source requirements for Supported events, and at least two distinct sources for any contradiction. An invalid result becomes a retryable error.

PRD: Analysis and Evidence Timeline; States and Boundaries.

5 · Show analysis and original sources

Files: public/app.js, public/styles.css. Render a calm, chronological workspace with accessible text labels for all evidence statuses. Original evidence is opened from the same in-memory file set.

PRD: Analysis and Evidence Timeline; Look and Feel.

6 · Open report from same result

File: public/app.js. Render a neutral report from the validated result object; do not make a second model call.

PRD: Evidence Report.

Keep it small

Tradeoffs and boundaries

Minimal setup

Plain browser code and Node's built-ins; no framework, database, account system, or deployment requirement.

Real AI in the demo

The synthetic packet uses the same live analysis route as uploads. The tradeoff is a required API key and internet connection.

Small controlled inputs

Five files max, fixed extensions and size limits. Other formats get a clear unsupported message.

Ephemeral data

Files/results disappear on refresh or close. No account or saved-case feature is introduced.

Source checks, not truth checks

The server verifies IDs and required citation fields; the reviewer can inspect the original. AI output can still be wrong.

Local demo is enough

Record the required short video from http://localhost:3000; deployment remains optional.

Data notice: Evidence is sent to Gemini for analysis. On the free tier, Google may use submitted content to improve its products. The landing/upload views and README must tell people to use fictional, non-sensitive evidence only.

Canonical technical plan: spec.md. This visual companion is standalone and works without a build step or network connection.
