One clear path from scattered evidence to a verifiable story.

The scope named the small experiment. This PRD makes the user journey, evidence rules, and failure recovery concrete enough to build and check.

Two entries, one analysis

The complete user journey

Landing · choose demo or upload
Demo path · Try Demo Packet → finished analysis
Upload path · Select files → review/remove → Analyze Evidence → analysis
Shared analysis · Summary → source-linked timeline → status and gaps → report. Original files stay accessible.
Try Demo Packet

Open the completed fictional purchase analysis immediately; the user does not need to inspect source files first. The analysis keeps an action to view those originals.

Check Demo opens the same analysis structure as uploads and exposes its source files.

Upload and review

Select a small supported set. Show each filename, type, and basic file information, allow removal/replacement, and require an explicit Analyze Evidence action. No folders or case management.

Check The list reflects selected files; removing a file updates it; an empty or invalid set explains what to fix.

Processing and recovery

Show a lightweight processing state. For a failure, identify the file/reason when known, preserve the selection, allow remove/replace/retry, and keep successfully processed evidence available. If the service is unavailable, offer Retry analysis.

Check No failure path silently drops files or shows invented extracted evidence/statuses.

Analysis view

Show a short case summary, chronological timeline, source file per event, extracted detail, Supported / Uncertain / Missing state, concise Missing Evidence, and contradictions only when evidence conflicts. Original files and report are accessible here.

Check Each Supported event links to direct source evidence; ordering is chronological; no contradiction is shown for a mere gap.

Evidence report

Present the same source-grounded summary, events, statuses, relevant contradictions, and missing evidence in readable neutral language. Include the role/limits note.

Check The report never turns an uncertain or missing claim into a fact and is available after successful analysis.

Empty and invalid states

When no valid files remain, explain that at least one supported file is needed. Identify invalid/unsupported items and offer removal or replacement; do not begin analysis with an empty set.

Check The user can recover without returning to the start of the flow.

Evidence rules

Status describes the submitted records

Every timeline event follows: Event → Status → Source evidence → Extracted supporting detail. Never infer a fact because it seems plausible or follows logically from another event.

SupportedDirect support in one or more files; cite the file and relevant text, date, amount, or detail.
UncertainRelevant indication exists but is ambiguous, incomplete, or in conflict.
MissingThe files do not establish the event; identify evidence that could help verify it.

Contradictions: compare explicit details across sources and flag incompatible claims only. A missing delivery receipt alone is a gap, not proof of a contradiction. The product organizes evidence; it does not establish legal truth.

Scope gut check

Complete enough to demonstrate; constrained enough to build

What is sharp

The two entry routes converge on a single source-grounded result, with one memorable delivery-uncertainty example. Status definitions and failure recovery prevent the AI from making the evidence look more complete than it is.

What stays soft for the spec

Exact file formats, count/size limits, and whether the demo uses live analysis need to be chosen in the technical spec. Keeping those limits small is essential to the 2–4 hour target; no broad parsing or case-management layer belongs in this build.

Canonical requirements are in prd.md. The approved scope remains the project boundary.
